# Performance Query Audit — Implementation Report

**Date**: 2026-08-26  
**Branch**: `development`  
**Status**: Completed  

---

## Summary

This phase eliminates per-ticket N+1 query candidates in scanner services, converts report data materialization to SQL aggregates, and adds precomputed existence flags to the `TicketResource` list serialization path to prevent per-ticket relation-builder queries.

## What Changed

### 1. Scanner N+1 Removal

**Files**: `TicketSlaEscalationService.php`, `TicketInactivityReminderService.php`

- Preloads escalation/inactivity policies once per scan and passes the collection into per-ticket processing, eliminating per-ticket `SlaEscalationPolicy` and `InactivityPolicy` queries.
- Batches `TicketStatusHistory` lookups per chunk via `whereIn('ticket_id', ...)` with in-memory grouping.
- Preserves priority-specific-then-default policy precedence and all existing notification/deduplication behavior.

### 2. Report SQL Aggregates

**Files**: `TicketVolumeReportService.php`, `DeploymentReportService.php`

- `getAging()` now computes `AVG` and `MAX` age from a single SQL aggregate instead of hydrating every open ticket. Portable date-diff expressions handle both SQLite and MySQL.
- `getSummary()` now computes status totals and average deployment duration via SQL conditional aggregates. Median duration remains in PHP for SQLite/MySQL portability.

### 3. TicketResource List-Path N+1 Prevention

**Files**: `Ticket.php` (`scopeForSummary`), `TicketResource.php` (`allowedActions`)

Extended `scopeForSummary()` with boolean existence flags via `withExists`:

| Flag | Source | Purpose |
|---|---|---|
| `has_open_defects` | `qaDefects` (status IN open/in_progress/reopened) | Replaces per-ticket `qaDefects()->exists()` in DevelopmentInProgress branch |
| `has_open_uat_finding` | `uatFindings` (status IN open/in_progress/reopened) | Replaces per-ticket `uatFindings()->exists()` |
| `has_any_defect` | `qaDefects` (unfiltered) | Summary information |
| `has_any_uat_finding` | `uatFindings` (unfiltered) | Summary information |
| `has_qa_failed_history` | `histories` (to_status = qa_failed) | Replaces per-ticket `histories()->where()->first()` |
| `has_uat_failed_history` | `histories` (to_status = uat_failed) | Replaces per-ticket `histories()->where()->first()` |
| `has_rework_worklog` | `worklogs` (activity_type = rework) | Replaces per-ticket `worklogs()->exists()` |
| `has_passed_internal_test` | `internalTestRuns` (status = passed) | Replaces per-ticket `internalTestRuns()->exists()` |
| `has_active_internal_test` | `internalTestRuns` (status = in_progress) | Replaces per-ticket `internalTestRuns()->where()->exists()` |

`TicketResource::allowedActions()` now detects whether these flags are present (list path via `forSummary`) and uses them for the `DevelopmentInProgress` retest-eligibility checks. Detail endpoints that load `histories`/`worklogs`/`internalTestRuns` relations fall through to the original timestamp-correlated per-ticket queries for exact precision.

**Design decision**: The list path uses simplified existence flags (e.g., "any rework worklog exists" rather than "rework worklog exists after last failure timestamp"). This is intentional — list payloads surface candidate actions, and the exact eligible set is recomputed on the detail endpoint where those relations are eager-loaded. The performance benefit outweighs the slight action-list imprecision for the narrow subset of tickets with open defects and a qa/uat-failed history.

### 4. Regression Tests

**Files**: `TicketSlaEscalationNplus1Test.php`, `TicketInactivityReminderNplus1Test.php`, `TicketResourceSerializationNplus1Test.php`, `ReportCalculationPerformanceTest.php`, `TicketListQueryPerformanceTest.php`, `TicketResourceListNplus1Test.php`

- Scanner tests prove escalation/inactivity policies are loaded once per scan regardless of ticket count.
- Serialization regression test proves list endpoints do not issue per-ticket `qaDefects`/`worklogs`/`internalTestRuns` queries.
- Query-count comparison tests prove PIC and Supervisor IT list serialization query counts do not scale with ticket count.
- Report tests verify SQL aggregate correctness for aging, deployment summary, and SLA compliance.

## Design Decisions

1. **List-path flags vs detail-path precision**: `allowedActions()` uses simplified precomputed flags on list paths and falls back to exact timestamp-correlated queries on detail paths. This avoids inflating list payloads while preserving action-list accuracy for the single-ticket detail view.

2. **Portable SQL aggregates**: Date-diff and average-duration expressions use SQLite/MySQL driver detection. Median/percentile calculations remain in PHP for portability.

3. **Scope-based reuse**: All precomputed flags live in `scopeForSummary()` to benefit every controller that uses `Ticket::forSummary()` (PIC, Supervisor IT, IT Lead).

## Limitations and Remaining Work

- **Timestamp-correlated retest eligibility**: The list path uses simplified existence flags for `submit_qa_retest`/`submit_uat_retest` actions. The exact timestamp-correlated checks (`worklogs` after `lastFailure->created_at`) run only on the detail endpoint. This means a ticket might appear to have the retest action on the list but not on detail (or vice versa) for the narrow case of tickets with open defects + qa/uat-failed history. The impact is minimal since the action is informational on list and authoritative on detail.
- **Production-scale measurements**: This increment proves query counts do not scale with ticket count under test conditions. Real-world p95 latency measurements under production load remain pending.
- **MySQL CI validation**: All tests run on SQLite in-memory. The CI `backend-mysql` job validates migrations against MySQL 8.4; actual query performance under MySQL should be verified in staging.

## Improvements Implemented

1. **Scanner Optimization**:
   - **TicketSlaEscalationService**: Preloads escalation policies and batches status history queries per scan, reducing query count from O(N) to O(1) per scan.
   - **TicketInactivityReminderService**: Same optimization pattern applied for inactivity policies.

2. **Report Performance**:
   - **TicketVolumeReportService**: Replaced per-ticket hydration with SQL `AVG` and `MAX` functions for aging metrics.
   - **DeploymentReportService**: Uses SQL `SUM` and `AVG` with conditional expressions for status counts and average duration.

3. **Serialization Efficiency**:
   - **TicketResource**: Added precomputed existence flags (e.g., `has_open_defects`, `has_qa_failed_history`) to `scopeForSummary()`. This allows list views (PIC, Supervisor IT, IT Lead) to check ticket properties without per-ticket relation queries.
   - **Action Logic**: `allowedActions()` uses these flags on list paths and falls back to exact timestamp-based queries on detail paths for precision.
